### Root cause (one sentence)

The Nebula-pivot dumb-pipe tunnel never called
`setsockopt(SO_RCVBUF / SO_SNDBUF)`, so every `UdpSocket` inherited the
system default (`net.core.rmem_default`, ~200 KB - 1 MB). The dumb-pipe
has zero retransmit, so under concurrent load any kernel-level rcvbuf
overflow becomes a permanent transfer stall.

### Evidence trail (preserved in case anyone wants to re-verify)

- `/tmp/ms-debug.log` — original instrumented multistream run showing
  the per-stream sender vs receiver `TunnelStats` divergence.
- `/tmp/ztlp-multistream/stream-*.log` — last bench's per-stream logs.
- Counter invariant proved by trial-by-trial `/proc/net/snmp` diff:
  `dIn + dInErr == dOut` every time (every UDP packet either
  delivered or `RcvbufErr`-dropped).
- Per-bridge `TunnelStats` for a stalled stream:
  ```
  sender:   tx_tcp=10.0MB  pkts_sent=8800  pkts_drop=0  retransmits=0
  receiver: rx_tcp= 6.0MB  pkts_recv=5242  pkts_drop=0  retransmits=0
  ```
- `ss -uan` snapshot during a 4-stream stall caught a receiver socket
  at Recv-Q = 621,312 bytes (~607 KiB) before drops started.

### Fix (3 files, 119 lines)

- `proto/src/gso.rs` — new `set_udp_buffer_sizes(socket, rcv, snd)`
  helper. Tries `SO_RCVBUFFORCE`/`SO_SNDBUFFORCE` first (bypasses
  `rmem_max` cap when caller has `CAP_NET_ADMIN`, e.g. iOS NE,
  root-launched relay), falls back to `SO_RCVBUF`/`SO_SNDBUF`. Logs
  actual kernel rcvbuf at debug. Non-Linux is a no-op.
- `proto/src/tunnel.rs` — call it from `run_bridge_inner` for both the
  primary tunnel socket and the optional demuxed recv socket.
  Constant `TUNNEL_UDP_BUF_BYTES = 7 MiB` matches the standard
  ZTLP-tuned host's `net.core.rmem_max`.
- `proto/src/bin/ztlp-throughput.rs` — comment-only, noting the
  lib-level tune covers it.

All ZTLP consumers (`ztlp-cli`, `ztlp-throughput`, `ztlp-relay-demo`,
iOS NE FFI, Tauri desktop, server-side bridges) flow through
`run_bridge_inner`, so they all get the tune automatically with no
per-binary changes.

The fix greatly widens the loss-free window, but the dumb-pipe still
has no retransmit. A host pegged for tens of ms during a burst could
still drop. If we ever see this in production WAN traces:
- Don't port the iOS separate-ACK-socket pattern wholesale — the

## Anti-patterns recorded this session (do not repeat)

1. Don't trust sysctl tuning alone. `net.core.rmem_max = 7 MiB`
   without `setsockopt` only raises the *cap*. Apps must opt in.
2. Don't assume "OK trial = clean transfer." Counter-diff
   accounting via `/proc/net/snmp` is the source of truth; userspace
   `pkts_drop` stays at zero for kernel-level drops because those
   happen *before* the socket queue.
3. Don't reach for "port the iOS ACK socket" when the symptom looks
   like ACK starvation. The dumb-pipe has no ACK consumer; that fix
   would build infrastructure for a layer that isn't there. The
   plan caught this; runtime evidence confirmed it.
4. `cargo test --test throughput_regression_test` MUST be run with
   `--release`. Debug-profile builds drop below the 10 MB/s floor on
   a 2-core VM and produce a false failure.
