## Root cause

Three send paths in `proto/src/{tunnel,transport,ack_socket}.rs` were
computing the layer-3 HMAC tag over an AAD where `header.payload_len = 0`,
then setting `header.payload_len = ciphertext.len()` BEFORE serializing
the header. The on-wire bytes [44..46] (which the receiver reads back as
part of its AAD at `pipeline::layer3_auth_check`) thus contained the real
payload length, but the tag had been computed assuming zero. 100%
rejection rate from packet 1.

The original tcpdump+RUST_LOG probe captured 884 of 885 packets failing
`auth_tag_invalid (rx)` in 5 ms, then 15 s of silence until the bench
timed out.

## Fix

One line moved in each of three sites:

```rust
// Before:
let mut header = DataHeader::new(session_id, seq);
let aad = header.aad_bytes();
header.header_auth_tag = compute_header_auth_tag(&send_key, &aad);
header.payload_len = encrypted.len() as u16;   // ← too late

// After:
let mut header = DataHeader::new(session_id, seq);
header.payload_len = encrypted.len() as u16;   // ← before AAD
let aad = header.aad_bytes();
header.header_auth_tag = compute_header_auth_tag(&send_key, &aad);
```

## Why my earlier diagnoses were wrong (recorded for honesty)

- **"Standardize DATA_HEADER_SIZE at 50 bytes"** — wrong. Header is 46
  bytes on the wire. The "50" figure was a miscalculation that
  propagated through an earlier handoff. Reverted.
- **"Make AAD contiguous"** — premature optimization. AAD layout was
  not the bottleneck. After the payload_len fix, microbench layer-3
  ceiling (1.19 M ops/sec) is not the limit either — the loopback
  pipeline ceiling on this host is somewhere above 250 MB/s.
- **"Port separate-ACK-socket from iOS"** — wrong failure mode. That
  fix targets window starvation under valid traffic. Here the traffic
  was never valid in the first place. Real ZTLP loopback may eventually
  benefit from it once headroom is exhausted, but it's not the next
  bottleneck.

## Microbenchmarks (unchanged — these were always healthy)

From `proto/target/release/ztlp-bench`:

| Stage                                | Throughput        |
| ------------------------------------ | ----------------- |
| HandshakeHeader::serialize           | 32.1 M ops/sec    |
| DataHeader::serialize                | 40.1 M ops/sec    |
| DataHeader round-trip                | 39.9 M ops/sec    |
| layer1_magic_check                   | 55-56 M ops/sec   |
| layer2_session_check (10k sessions)  | 32-38 M ops/sec   |
| layer3_auth_check (valid HMAC)       | **1.19 M ops/sec**|
| Full pipeline (valid packet)         | **1.18 M ops/sec**|

At 1400-byte payloads the pipeline ceiling is ~1.65 GB/s — comfortably
above the current 243 MB/s end-to-end ceiling. The remaining gap to
Raw TCP (~10x) is probably real transport (no GSO, single-threaded
recv, no batching) — that's where the next round of work should go.

## Next steps (now that ZTLP actually moves bytes)

1. **Land this PR.** One commit, 3 files, 6 lines. Tests green. Bench
   green.
2. **Add a regression test.** An in-process two-tunnel bridge that
   pushes ~1000 packets through and asserts the pipeline's
   `layer3_drops` counter stays at 0. The fact that 776 unit tests
   missed this for however long is a gap.
3. **Then optimize transport.** With the receiver actually accepting
   packets, the remaining 10x gap to Raw TCP is candidate territory:
   - GSO enable on Linux (currently "unavailable" — investigate why)
   - recv batching / `recvmmsg`
   - separate ACK socket (now relevant — see iOS skill for pattern)
   - reduce per-packet allocations (`aad_bytes()` returns a `Vec`)
