## Root cause

The Nebula-pivot R3 dumb-pipe (`proto/src/tunnel.rs::run_bridge_inner`)
has **no retransmit** — fire-and-forget `sendto`, decrypt-and-deliver on
RX with replay-bitmap admission, zero ACK/NACK consumption. Each kernel-
level UDP drop is therefore a *permanent* transfer stall.

ZTLP never called `setsockopt(SO_RCVBUF / SO_SNDBUF)`. So every
`UdpSocket` inherited `net.core.rmem_default` (~200 KB - 1 MiB depending
on distro). The earlier sysctl tuning (`rmem_max = 7 MiB`) raises only
the *cap*; applications must explicitly request the bigger buffer.

Under N>=2 concurrent tunnels on a single host the loopback bursts
overflow the small default rcvbuf, the kernel drops packets at the
destination socket (recorded as `UdpInErrors / UdpRcvbufErrors` in
`/proc/net/snmp`), and any FRAME_DATA loss becomes an irrecoverable
hole in the receiver's TCP byte stream — the harness times out after 60s
with `received X of Y bytes`.

### Evidence that nailed it

Trial-by-trial counter diff at N=2 (5 trials, 10 MB each direction):

```
trial=1 s0=0MB/s(rx=4245006) s1=71MB/s(FULL)  dIn=8440  dInErr=9180  dOut=17620
trial=2 s0=78MB/s(FULL)      s1=89MB/s(FULL)  dIn=10892 dInErr=6717  dOut=17609
trial=3 s0=0MB/s(rx=7686504) s1=83MB/s(FULL)  dIn=11417 dInErr=6206  dOut=17623
trial=4 s0=93MB/s(FULL)      s1=0MB/s(rx=3969390) dIn=9009 dInErr=8612 dOut=17621
trial=5 s0=94MB/s(FULL)      s1=92MB/s(FULL)  dIn=11347 dInErr=6263  dOut=17610
```

Invariant: `dIn + dInErr == dOut` every trial. **Every UDP packet
that was sent either delivered or was RcvbufErr-dropped.** Stalls
correlate with which stream happens to lose a FRAME_DATA.

Per-bridge `TunnelStats` from a stalled stream (N=8 run, stream-1):

```
sender:   tx_tcp=10.0MB  tx_udp=10.6MB  pkts_sent=8800  pkts_drop=0  retransmits=0
receiver: rx_tcp= 6.0MB  rx_udp= 6.3MB  pkts_recv=5242  pkts_drop=0  retransmits=0
harness:  Backend read timeout (received 6,245,886 of 10,485,760 bytes)
```

3,558 packets / 4.3 MB sent by the sender never arrived at the receiver's
userspace recv loop. `pkts_drop=0` on the receiver — confirming the loss
was *kernel-level* (drops before the socket queue) not userspace.

Live `ss` snapshot during a 4-stream stall caught a receiver socket
backed up at **Recv-Q=621,312 bytes** (~607 KiB) — already higher than
typical small-default rcvbuf would tolerate before drops start.

The plan's other hypotheses ruled out:
- **NOT** tokio scheduler starvation — sender's `pkts_sent` keeps growing
  cleanly until all 8800 frames are emitted.
- **NOT** TCP backpressure — sender's TCP-read time is < 6 % of elapsed.
- **NOT** an ACK-consumer gap — the dumb-pipe has none, so there's
  nothing to starve. Porting the iOS separate-ACK-socket pattern would
  build infrastructure for a protocol layer that isn't there. The plan
  already called this out; runtime evidence confirms it.

## Fix

`proto/src/gso.rs`: new helper `set_udp_buffer_sizes(socket, rcv, snd)`
that uses `SO_RCVBUFFORCE / SO_SNDBUFFORCE` first (bypasses `rmem_max`
cap when caller has `CAP_NET_ADMIN`, e.g. iOS NE, root-launched relay),
falling back to `SO_RCVBUF / SO_SNDBUF`. Best-effort: errors logged at
debug and swallowed; non-Linux is a no-op.

`proto/src/tunnel.rs::run_bridge_inner`: call `set_udp_buffer_sizes` on
both the primary tunnel socket and the optional demuxed recv socket
right after the bridge starts. Constant `TUNNEL_UDP_BUF_BYTES = 7 MiB`.

All ZTLP consumers (`ztlp-cli`, `ztlp-throughput`, `ztlp-relay-demo`,
the iOS NE FFI, the Tauri desktop) go through `run_bridge_inner` or
one of its public wrappers, so they all get the buffer tune
automatically. No per-binary changes required.


Kernel reports `actual=14680064` (14 MiB) for a 7 MiB request — kernel
internally accounts skb overhead by doubling.

## Caveats / what we did not change

1. The dumb-pipe still has **no retransmit**. The buffer tune greatly
   widens the loss-free window, but a host that's truly overcommitted
   (e.g. CPU-pegged for tens of milliseconds while a burst arrives) can
   still drop. A real reliability layer remains a separate question; it
   is not needed for the current Nebula-pivot R3 use cases (the end
   systems retransmit at the TCP layer, which is exactly what the
   loopback harness exercises — TCP retransmit can't fix dumb-pipe loss
   because the dumb-pipe is *inside* the encrypted tunnel).
2. The fix targets ZTLP-internal tunnel sockets only. The Gateway's
   inbound socket and the Relay's hub socket are different code paths
   that would benefit from the same setsockopt; that's `ztlp-load
   gateway` / full-stack work (plan Objective B3) and out of scope here.
3. `SO_RCVBUFFORCE` requires `CAP_NET_ADMIN`. On hosts without it the
   call silently falls through to `SO_RCVBUF` and the kernel caps at
   `rmem_max`. Verify with the debug log:
   `set_udp_buffer_sizes: requested rcv=7340032 ... actual=N` — if N
   is much smaller than 14 MiB, increase `net.core.rmem_max` on the
   host (the existing `ztlp-validation-suite` step 1b already does this
   on production deployments).
