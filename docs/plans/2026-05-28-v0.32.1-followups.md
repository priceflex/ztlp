## Highest risk + mitigation

**T1 (keepalive port plumbing) is the riskiest task** because changing the `PunchAgent` constructor signature touches both the `proto` library API and the `bin/ztlp-cli.rs` listener wiring. If the field semantics are wrong, every gateway in the field publishes broken candidates again.

**Mitigation:** the existing test `keepalive_packet_includes_local_candidates_with_listener_port` at `punch_agent.rs:596` ALREADY asserts the contract: "candidates published by the keepalive carry the LISTENER port, not the keepalive socket port." That test is the spec — make it pass with two sockets present in production (today it passes accidentally because tests use a single socket as both keepalive AND listener).

**Pre-flight that's already done:** I read the constructor at `punch_agent.rs:118-128` — it captures `socket.local_addr().port()` as `listener_port`. The fix needs a NEW constructor variant `with_listener_port(socket, ns_addr, node_id, listener_port, ...)` that DECOUPLES the listener port from the keepalive socket. Then `ztlp-cli.rs:4218-4234` plumbs the QUIC server's `inner.local_addr().port()` through.

**T2 (IPv6 dual-stack) risk is lower** — purely additive. Today's `QuicDialer::new()` returns `Err` on `Address family not supported` and the orchestrator already handles per-candidate errors gracefully (verified in the M9 bench logs).
