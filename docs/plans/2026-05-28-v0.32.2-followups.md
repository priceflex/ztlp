# v0.32.2 follow-ups — multi-candidate works end-to-end via NS name

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** `ztlp connect --multi-candidate --ns-server ... <name>` actually completes a data-plane handshake LAN-direct, so SSH-through-ZTLP-tunnel works for NS-named targets the same way it works for raw-IP targets today.

**Architecture:** Move the M6 multi-candidate dial out of the legacy-UDP path and into the QUIC path. Today M6 is correctly setting `send_addr` to the LAN winner, but it lives inside the legacy-UDP code branch which is broken end-to-end against the v0.30 production relay. The QUIC path is the path that actually works (proven: `ztlp connect 10.170.3.111:23095 --service ssh -L 2240:127.0.0.1:22` → real SSH session to `DESKTOP-LRC8DKH`). Multi-candidate logic just needs to live there too.

**Tech stack:** Rust 1.75+, tokio, quinn. No Elixir/NS changes.

### Step 3: Wire helper into QUIC path

In `bin/ztlp-cli.rs`, AFTER `let (peer_addr, peer_node_id) = resolve_target(target, ns_server).await?;` (line ~3254) and BEFORE the CLIENT_ROUTE block (line ~3283), add the multi-candidate dial:

```rust
// v0.32.2 (A1): multi-candidate dial moved from legacy path to QUIC path.
//
// When --multi-candidate is set AND we have an NS-resolved peer NodeID,
// race the host candidates from PUNCH_REPORT alongside the NS-resolved
// peer_addr (which is typically the relay). The winning path's address
// overrides peer_addr for the rest of this function — CLIENT_ROUTE +
// QUIC handshake then both target the winner.
//
// Failure (no winner, NS query timeout, all candidates unreachable)
// falls back to using the NS-resolved peer_addr unchanged — same
// outcome as if --multi-candidate weren't passed at all. This is the
// "safe default" the M6 commit was designed around.
let multi_candidate_winner: Option<SocketAddr> = if multi_candidate && peer_node_id.is_some() {
    if let Some(ns_str) = ns_server.as_deref() {
        if let Ok(ns_addr) = ns_str.parse::<SocketAddr>() {
            eprintln!(
                "{} multi-candidate dial enabled (v0.32.2)",
                c_dim("[v0.32.2]")
            );
            // Note: we use a TEMPORARY tokio socket for the probe, not
            // the std_socket Quinn will take over. Quinn needs a fresh
            // std::net::UdpSocket; using the probe socket would put us
            // in the same fd-sharing trap that v0.31's punch hit.
            let probe_sock = match tokio::net::UdpSocket::bind("0.0.0.0:0").await {
                Ok(s) => std::sync::Arc::new(s),
                Err(e) => {
                    eprintln!(
                        "{} multi-candidate probe socket bind failed: {}; falling back to NS-resolved addr",
                        c_dim("[v0.32.2]"),
                        e
                    );
                    None
                        .or_else(|| -> Option<SocketAddr> { None })
                        .map(|x| -> SocketAddr { x });
                    // sentinel: this whole branch returns None below
                    return Ok(()); // unreachable in practice
                }
            };
            let policy = ztlp_proto::dial_orchestrator::DialPolicy::default();
            let local_subnets = ztlp_proto::local_candidates::our_local_subnets();
            match ztlp_proto::multi_candidate_dial::try_multi_candidate_connect(
                peer_node_id.unwrap(),
                ns_addr,
                probe_sock,
                identity.node_id,
                &local_subnets,
                Some(peer_addr),
                policy,
            )
            .await
            {
                Ok(outcome) => {
                    eprintln!(
                        "{} multi-candidate dial succeeded: {} ({:?})",
                        c_green("✓"),
                        outcome.winning_addr,
                        outcome.class
                    );
                    Some(outcome.winning_addr)
                }
                Err(e) => {
                    eprintln!(
                        "{} multi-candidate dial failed: {:?}; falling back to NS-resolved addr",
                        c_dim("[v0.32.2]"),
                        e
                    );
                    None
                }
            }
        } else {
            None
        }
    } else {
        None
    }
} else {
    None
};

let peer_addr = pick_quic_dial_target(peer_addr, multi_candidate_winner);
```

**SIMPLIFY the error-handling sketch above** — the orchestrator's draft is awkward Rust because of the nested-Option-return pattern. The real implementation should:

1. Compute `multi_candidate_winner: Option<SocketAddr>` via clean `match` blocks.
2. Reassign `let peer_addr = pick_quic_dial_target(peer_addr, multi_candidate_winner);`.
3. Continue with CLIENT_ROUTE + QUIC handshake using the new `peer_addr` unchanged.

Do NOT use `--punch` / `--punch_enabled` as a condition — that's the bug we're fixing. The ONLY conditions are `multi_candidate` flag + presence of `peer_node_id` + parseable `ns_server`.

### Step 2: GREEN — family-matched send

The fix pattern (from T2):

```rust
let bind_addr = match candidate_addr {
    SocketAddr::V4(_) => "0.0.0.0:0",
    SocketAddr::V6(_) => "[::]:0",
};
let send_sock = UdpSocket::bind(bind_addr).await?;
send_sock.send_to(&packet, candidate_addr).await?;
```

If `execute_punch` reuses a single shared socket (`node.socket`), the simplest fix is to detect family mismatch before send and silently skip the send (don't return an error to the dispatcher) — IPv6 sends from an IPv4-only socket can't work; logging a warning once is sufficient.

Either approach is acceptable. **Document the decision in the commit message.**
