# v0.34.0 — Granular registration error codes

## What

Replace the opaque `<<0xFF>>` registration-rejection wire response with `<<0xFF, reason::8>>`, where the second byte encodes a specific reason code. CLI parses the reason and shows the user actionable text instead of "rejected (invalid data format)".

## Why

Before v0.34, when an NS registration failed, every failure path returned the same `<<0xFF>>` byte. A client couldn't tell `:rate_limited` from `:invalid_signature` from `:key_overwrite_rejected` from `:storage_error`. This made:

- **CLI errors useless** — users got "NS server rejected the request" with no path to diagnosis.
- **A client daemon impossible to write correctly** — the v0.33.0 follow-up (background heartbeat to keep KEY records fresh) needs to know whether a failure is transient (`:rate_limited` → back off and retry) or terminal (`:revoked_pubkey` → stop forever, alert the user).

## Wire format

```
<<0xFF, reason_code::8>>
```

| Code | Symbol              | Meaning                                                          |
|------|---------------------|------------------------------------------------------------------|
| 0x00 | `unspecified`       | Catch-all when no specific code applies                          |
| 0x01 | `unknown_type`      | Record type byte not in the known type enum                      |
| 0x02 | `missing_pubkey`    | Used v1 (0x09) registration in prod where v2 (0x0A) is required  |
| 0x03 | `invalid_name`      | Name validation failed (suffix mismatch, format invalid)         |
| 0x04 | `invalid_signature` | Ed25519 signature verification failed                            |
| 0x05 | `unauthorized`      | Pubkey not allowed to register this name/type (zone auth)        |
| 0x06 | `key_overwrite`     | Another pubkey already owns this name (DEVICE/USER protection)   |
| 0x07 | `revoked_pubkey`    | The pubkey or its NodeID has been revoked                        |
| 0x08 | `revoked_name`      | The name itself has been revoked                                 |
| 0x09 | `rate_limited`      | Hit the per-name registration rate limit                         |
| 0x0A | `invalid_data`      | CBOR decode failed or type-specific field validation failed      |
| 0x0B | `storage_error`     | Mnesia / Store.insert failed (stale_serial retry exhausted)      |

## Backward compatibility

Pre-v0.34 clients only inspect byte 0 (`0xFF`) and ignore everything after. They continue to receive an opaque "rejected" signal exactly as before. New clients that parse byte 1 get a granular reason they can use to drive backoff / retry / give-up logic.

The opposite direction is also safe: the CLI's `decode_registration_error` helper handles bare 1-byte responses (old NS) and unknown reason codes (newer NS than this client knows about).

The `proto` floor in `version_pin_test.rs` stays at `0.32.2` — this release is **additive** and does not require a fleet-wide upgrade.

## Scope (what's in vs. out)

**In:**
- New `ZtlpNs.RegistrationError` Elixir module with full encode/decode/from-internal mappings.
- All 7 registration error sites in `ns/lib/ztlp_ns/server.ex` updated to emit granular codes.
- New `decode_registration_error/1` helper in `proto/src/bin/ztlp-cli.rs`.
- Both CLI sites in `cmd_ns_register` (KEY and SVC paths) display the granular message.
- 26 Elixir unit tests + 4 Rust unit tests + 7 affected integration tests updated.
- Versions bumped to `0.34.0` across all four manifests.

**Out (deliberately deferred):**
- Lookup-path errors (`<<0xFF>>` at server.ex:163 and the malformed-query catch-all at server.ex:433) stay opaque. Only registration paths gain reason codes — that's where the practical daemon-needs-this-to-back-off-correctly value lives.
- Other CLI call sites that handle `0xFF` (admin revoke, etc.) keep their existing handling; only `cmd_ns_register` gets the upgraded display today. They can be migrated incrementally as the daemon and admin tools need them.

## Tests

- `ZtlpNs.RegistrationErrorTest`: 26 tests covering encode/decode round-trips, internal-reason mapping, wire compatibility (byte 0 always 0xFF, response always 2 bytes).
- `decode_registration_error` Rust tests: 4 cases — old-server 1-byte handling, all known codes return rejection messages, named codes have useful text, unknown codes don't panic.
- Existing integration tests updated to assert granular codes: `security_hardening_test.exs` (3 sites), `group_test.exs` (1 site). Test stays at the v0.33.0 floor (`0.32.2`).

## Follow-up

This is a hard prerequisite for the v0.35.0 client daemon (`ztlp register --daemon`). The daemon's backoff loop needs `:rate_limited` (transient) vs. `:revoked_pubkey` (give up forever) vs. `:storage_error` (fast retry) to behave correctly. Without granular codes the daemon would treat every failure identically and either spam the NS or give up too soon.
