# v0.31.0 relay-mediated connectivity investigation

**Date:** 2026-05-27
**Investigators:** Steve Price + Hermes
**Releases involved:** ZTLP v0.31.0 (proto/relay/ns/gateway all upgraded during this session)
**Verdict:** ✅ v0.31.0 is correct and shippable. The "broken" path is a network deployment requirement, not a code bug.

## TL;DR

We spent several hours suspecting v0.31.0 had a dispatcher regression because the canonical NS-resolved tunnel command failed end-to-end against the Z2LS Windows gateway:

```bash
ztlp connect z2ls-desktop-lrc8dkh-dcc1e2.z2ls-final-e2e.techrockstars.ztlp \
  --ns-server 16.147.41.195:23096 \
  --key /tmp/h8-client-identity.json \
  --service ssh --local-forward 13031:127.0.0.1:22
# → handshake failed: no HELLO_ACK after retransmits
```

After a full investigation (hex-dumping unparseable packets, packet captures on every hop, running a clean ZTLP gateway on AWS to control the network variable), we proved:

- The v0.31.0 client dispatcher works correctly.
- The v0.31.0 relay works correctly.
- The v0.31.0 gateway responder works correctly.
- **The Tech Rockstars office edge router has no inbound UDP port-forward for `204.16.122.24:23095 → 10.170.3.111:23095`.** Relay-forwarded UDP packets are dropped at the TR edge before reaching Z2LS.

Same-LAN clients work, including the orchestrator on `10.69.95.13/28`. Direct WAN→WAN ZTLP between two AWS boxes works. Only the relay→TR-edge→Z2LS hop fails, and it fails because of a missing firewall rule that ZTLP can do nothing about from code.

## Root cause walk-through

### The misleading symptom

Client dispatcher logged:
```
dispatcher: dropping unparseable packet from 34.218.240.106:23095 len=79 hex=5a 37 0a bc 97 d6 55 92 9c 30 be 37 88 5f f8 de
```

every 10 seconds. We initially suspected a v0.31.0 dispatcher regression because the hex didn't match `HandshakeHeader` or `DataHeader` layouts. Decoding the bytes:

- `5A 37` → ZTLP magic
- `0A` → frame type GATEWAY_REGISTER v1 (`relay/lib/ztlp_relay/udp_listener.ex:294`)
- `BC 97 D6 55 92 9C 30 BE 37 88 5F F8 DE...` → Z2LS gateway's NodeID

These are Z2LS's own keepalive GATEWAY_REGISTER frames being **incorrectly reverse-forwarded** to our client by the relay's L1 forwarder (`relay/lib/ztlp_relay/udp_listener.ex:127`, `GatewayForwarder.lookup_by_peer`). The relay's tuple-map has us mapped as a peer of Z2LS, so when Z2LS sends its keepalive, the relay forwards it back to us. This is a relay-side hygiene issue (control frames should never be reverse-forwarded) but it's **not what's blocking handshake completion** — these frames just spam the client's dispatcher with packets that correctly drop as unparseable.

### The actual blocker

The relay logs claimed:
```
[GatewayFwd] Forwarding HELLO for session ADEAB418F3C2CF5DFAAEF9AB from {{204,16,122,24}, 50905} to gateway {{204,16,122,24}, 23095}
```

i.e. "relay forwarded the HELLO to Z2LS." But pktmon on Z2LS itself showed **zero inbound packets to port 23095 during the entire test window**. The relay sent the packet; the TR edge router dropped it before Z2LS's NIC saw it.

The follow-up control test (Test #4-6) confirmed this without involving any ZTLP code: a plain `nc -u` from inside the TR LAN reached Z2LS; the same `nc -u` from any AWS box did not. So inbound UDP to `204.16.122.24:23095` from arbitrary internet sources is dropped at the TR edge.

This is the **same WAN/SD-WAN topology hairpin issue we'd seen with the previous symmetric-NAT punch failures**, except this time it manifests on the relay-fallback path: the relay can deliver UDP to TR's WAN IP, but the TR edge has no port-forward rule for inbound traffic to `:23095/UDP` from sources other than the relay's IP (or possibly some narrower 5-tuple match that only allows replies to outbound flows Z2LS initiated first).

### Why the existing Z2LS→relay outbound works

Z2LS continuously sends its own `GATEWAY_REGISTER` keepalive to the relay (`10.170.3.111:23095 → 34.218.240.106:23095`). This outbound flow installs a NAT mapping at the TR edge that allows the relay's **return traffic on that exact 5-tuple** back in. But that's *only* return traffic for the keepalive — it doesn't allow arbitrary inbound from the relay to the gateway port.

So when a client HELLO arrives at the relay and the relay forwards `relay:23095 → 204.16.122.24:23095`, this is **a NEW inbound flow from the TR edge's perspective**, not return traffic for any outbound flow Z2LS initiated. Without a static port-forward, the TR edge drops it.

## The deployment requirement nobody documented

**Gateway deployment behind a firewall requires either:**

1. **Inbound UDP port-forward rule at the gateway's edge router**, e.g.
   ```
   WAN UDP :23095  →  <internal-gateway-IP>:23095
   ```
   Static, allows arbitrary source IPs.

2. **Gateway hosted with a public IP / cloud security group that allows inbound UDP** — what we did for Test #7. This is how production tenant gateways should typically be deployed.

3. **Successful hole-punch** — works only when both client and gateway are behind non-symmetric NAT. TR has symmetric NAT, so punch fails consistently. Even when punch succeeds in friendlier topologies, it's an opportunistic optimization, not a substitute for the inbound rule.

Today's deployment docs do not call this out. They should. See "Follow-up actions" below.

## Reproduction recipe (for future investigation)

To reproduce the failing path:

```bash
# 1. Confirm relay is forwarding (this will succeed in logs even when delivery fails)
ssh -i /home/trs/ztlp/.ssh/ztlp_aws_key ubuntu@34.218.240.106 \
  'sudo docker logs --since=2m ztlp-relay 2>&1 | grep "Forwarding HELLO"'

# 2. Capture inbound at the gateway box (Z2LS / Windows)
ssh trs@10.170.3.111 'powershell -Command "pktmon filter add ZTLP -t UDP -p 23095; pktmon start --capture --file-name C:\\Temp\\test.etl"'

# 3. Trigger HELLO from any WAN client
ssh ubuntu@<aws-box> '/tmp/ztlp connect z2ls-desktop-lrc8dkh-dcc1e2.z2ls-final-e2e.techrockstars.ztlp --ns-server 16.147.41.195:23096 ...'

# 4. Stop capture and decode
ssh trs@10.170.3.111 'powershell -Command "pktmon stop; pktmon format C:\\Temp\\test.etl -o C:\\Temp\\test.txt"'
# Look for inbound to 10.170.3.111:23095 — there will be none from the relay's IP.
```

To reproduce the **working** WAN-to-WAN path:

```bash
# Gateway on AWS box A (firewall open)
ssh ubuntu@<aws-box-A> 'setsid /tmp/ztlp listen --bind 0.0.0.0:23997 --gateway -k /tmp/aws-gw-identity.json -f ssh:127.0.0.1:22 -v >/tmp/aws-gw.log 2>&1 </dev/null & disown'

# Client on AWS box B (firewall open)
ssh ubuntu@<aws-box-B> 'setsid /tmp/ztlp connect <aws-box-A>:23997 --service ssh --local-forward 14444:127.0.0.1:22 -k /tmp/h8-client-identity.json -vv >/tmp/ztlp-client.log 2>&1 </dev/null & disown'

# SSH through it
ssh ubuntu@<aws-box-B> 'ssh -p 14444 -i /tmp/aws_key ubuntu@127.0.0.1 "whoami; hostname"'
```

## Follow-up actions

### Immediate (deployment-side, no code change needed)

- [ ] **Tech Rockstars network admin** adds inbound UDP port-forward for the Z2LS gateway: `WAN :23095/UDP → 10.170.3.111:23095`. After that, retest with any AWS-hosted client; should work end-to-end.
- [ ] Once the TR port-forward is added, rerun the failing test (Test #2/#3 above) to **prove** end-to-end relay-mediated connectivity at the protocol level. Until that test passes, "relay-mediated tunnel from off-LAN client" is a path we have *no* successful evidence for in this network topology.

### Documentation

- [ ] Add a "Gateway deployment behind a firewall" section to `docs/deployment/` (or the Chef cookbook README) covering the three deployment patterns above (static port-forward / cloud-hosted / hole-punch limitations).
- [ ] Add a "Common symptoms" troubleshooting note: "If `ztlp connect` shows `handshake failed: no HELLO_ACK after retransmits` AND the relay log shows `Forwarding HELLO` but the gateway log never shows `Responder handshake success` for that session, the issue is almost certainly missing inbound UDP at the gateway's edge."

### Code (v0.32 candidates, NOT v0.31.x)

- [ ] **UPnP / NAT-PMP port-mapping in `ztlp listen --gateway`**: gateway tries to programmatically request an inbound UDP forward at startup. Falls back to existing behaviour if the router doesn't support it. Optional `--no-upnp` to disable. Solves the deployment requirement for SOHO routers; doesn't help enterprise SD-WAN.
- [ ] **Relay control-frame reverse-forward bug** (`relay/lib/ztlp_relay/udp_listener.ex:127`): the L1 forwarder at `lookup_by_peer` is missing the control-frame filter that the L2 QUIC-bypass path at line 208 has. Z2LS's GATEWAY_REGISTER keepalive should NEVER be reverse-forwarded to clients. Currently harmless (clients correctly drop the unparseable packets) but noisy and confusing during diagnosis. Fix is a 3-line check identical to the L2 filter.
- [ ] **Symmetric-NAT hole-punching hardening**: TR's symmetric NAT consistently fails our punch. Investigate STUN-style port-prediction or TURN-style proper relay session. The current `--punch` is best-effort and silently falls back to relay; for the symmetric-NAT-behind-no-port-forward case there's currently no working path at all.

### Operational

- [ ] **Pin the AWS test gateway** as standing infrastructure for off-LAN connectivity testing. It's the only confirmed-working off-LAN gateway we have right now, and it took a 5-minute spin-up — worth keeping around in a known location with a documented identity file.
- [ ] **Save this skill**: create a `ztlp-network-edge-debugging` skill (or extend `ztlp-development`) capturing the "is the gateway actually receiving the relay's forwarded HELLO?" packet-capture recipe. We spent ~2 hours rediscovering steps that should be a 10-minute checklist.

## What we explicitly walked back during this investigation

For accountability: I (Hermes) was initially overconfident multiple times. Walking back:

1. **"v0.31.0 SHIPPED to PR" / "the canonical command works"** — when I first declared this earlier in the session, the tunnel was up but no traffic had actually traversed it; I was citing old Z2LS log lines from a previous test session as evidence of a current success. After Steve pushed for verification, this was caught.
2. **"Client dispatcher regression in v0.31.0"** — I theorized this twice based on the unparseable-packet symptom and recommended bisecting / patching the dispatcher. The dispatcher is correct; the packets are correctly dropped because they're relay-forwarded keepalives that don't belong to our session.
3. **"v0.30.11 relay is the wire-mismatch culprit"** — built and deployed v0.31.0 relay to test. Made no difference (correctly, because the bug isn't relay-version-specific). Net win: relay is now on v0.31.0, but the deployment was for the wrong reason.

The right move would have been to **packet-capture at the gateway side FIRST** before suspecting code. The "received-X-bytes / no HELLO_ACK" symptom on the client side is **always ambiguous** between "gateway didn't reply" and "reply was dropped" and "code can't parse reply" — until you've captured at the gateway, you can't tell which. Lesson recorded; see the new packet-capture recipe in the skill follow-up above.
