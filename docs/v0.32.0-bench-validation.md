## TL;DR

The load-bearing v0.32 claim — "gateways advertise local NIC addresses to NS so clients can dial them directly" — is **end-to-end validated on live AWS infrastructure.**

The v0.32 gateway running with `--advertise-all-interfaces` was observed to:
1. Enumerate 8 local NIC addresses on its host
2. Stuff them into `PUNCH_REPORT` (`0x0C`) keepalive frames
3. Send those frames to the production NS at `16.147.41.195:23096`
4. Have NS parse + store all 8 as `:reported` endpoints alongside the existing `:learned` endpoint

The client-side priority calculator (`candidate_priority::prioritize`) then correctly ranks the live NS-observed endpoint set against a simulated client subnet, placing the same-subnet host at priority 250 (top) and the relay at 50 (backstop).

**M1, M2, M4, and the NS-side parser from v0.31 are confirmed to interoperate on real infrastructure.** No production tenant or Z2LS bench was touched.

## What did NOT get validated live (and why)

### a) `ztlp gateway candidates v032-test.v032.ztlp` admin command

The new M7 admin command needs to resolve the gateway NodeID via NS KEY-record CBOR field `node_id`. The bare `ztlp ns register` debug command writes a KEY record but **does not include the `node_id` CBOR field** — a pre-existing NS limitation that pre-dates v0.32. The command errors with:

```
error: could not resolve NodeId for gateway 'v032-test.v032.ztlp' via NS at 16.147.41.195:23096 (no KEY record?)
```

In production deployments, gateways register via the launch flow which writes a full KEY record including `node_id`. **Tracked as a v0.32.1 fix candidate**: either teach `cmd_gateway_candidates` to accept a raw NodeID hex argument, OR fix `ns register` to populate `node_id` in the KEY record CBOR.

The underlying NS query path (PEER_ENDPOINTS via raw NodeID) IS functional, as proven in Step 5 above — the limitation is purely in the resolve-name-to-NodeID hop.

### b) Real `ztlp connect <name> --multi-candidate` end-to-end

The same NodeID-resolution limitation affects M6's `--multi-candidate` flag, which is gated on `_resolved_node_id.is_some()`. Without a NodeID in the KEY record, the multi-candidate path silently falls through to the legacy v0.31 path. **This is the correct behaviour** per M6's safe-fall-through design — but it means we couldn't observe the full parallel-dial in flight from a real client. The path IS tested under `cargo test --lib multi_candidate_dial` (8 BDD tests with fake NS + fake dialers).

### c) Z2LS bench (the actual v0.31 failure topology)

Per the task brief: not touched. Steve's bench is the gold-standard validation but requires Steve to deploy the v0.32 binary onto the Z2LS Windows gateway and run a connect from the orchestrator workstation. That deploy is **a Steve-driven RC step**, not an autonomous M9 step.

When Steve is ready, the procedure is:

2. Stop the existing v0.31 Z2LS gateway service (NSSM)

5. From a workstation on the TR LAN (e.g. `10.69.95.13`), run `ztlp connect z2ls --ns-server 16.147.41.195:23096 --punch --multi-candidate -v` and observe whether the new path wins
6. Expected: log line `[v0.32] multi-candidate dial succeeded: 10.170.3.111:23095 (hostsamesubnet)` followed by an SSH session that does NOT round-trip through the relay

### NSSM AppParameters UTF-16 pitfall (DEPLOY PITFALL, save for future runs)

`nssm get ztlp_listener AppParameters` echoes the stored value as raw UTF-16 bytes (every character followed by `\0`). The first deploy script naïvely did string-append on this output and fed the result back into `nssm set`, which corrupted the parameters and prevented the service from starting. The rolled-back deploy v2 rewrites the parameter string from a clean ASCII source-of-truth.

**Rule:** never round-trip `nssm get` output into `nssm set`. Always write from a known string literal.

**Observations:**

a) **Orchestration is wired correctly.** The `[v0.32]` log lines confirm `cmd_connect` enters the multi-candidate path when the flag is set + NS resolves a NodeID. All 7 candidates are dialed in parallel (host band + srflx band + relay band per M5 design). On total failure the code falls through cleanly to the v0.31 punch path with `send_addr` untouched per M6's safe-fall-through design.

b) **v0.32.1 limitation #1 (keepalive socket port mismatch) is BITING IN PRODUCTION.** Every candidate is being dialed at port `50592` — the gateway's ephemeral keepalive socket port — instead of `23095` where the listener actually is. The Z2LS gateway has no UDP listener on `50592`, so probes time out. This is exactly the limitation flagged in M9's original findings; the Z2LS bench just made it concrete. **This single fix is the gating item for `--multi-candidate` default-on at v0.32.0 release.**

c) **v0.32.1 limitation #4 (NEW — IPv6 QuicDialer):** the QuicDialer binds an IPv4-only socket (`0.0.0.0:0`) so all 3 IPv6 candidates fail at `send_to` with EAFNOSUPPORT. Should either bind dual-stack (`[::]:0`) or skip non-matching family candidates pre-dial.

### Net effect on v0.32.0 release plan

- The **discovery half** of the feature works end-to-end on the canonical Z2LS topology. Gateways publish, NS stores, clients (via M7 admin command + M6 multi-candidate orchestration) consume the candidate set correctly.
- The **dial half** has the orchestration wired right but is blocked on the keepalive-port-mismatch fix (M2 future work) before it can deliver actual LAN-direct connectivity.
- `--multi-candidate` stays hidden (`hide = true`) for v0.32.0 ship. The two v0.32.1 limitations (port mismatch, IPv6 family) are the gating items for the default-on flip.
- The v0.31 investigation's debugging pain is **already** solved by M7 alone — operators can now see what NS knows about a gateway in 5 seconds. That's worth shipping by itself, with `--multi-candidate` as an opt-in beta.

### v0.32.1 candidates after Z2LS bench

1. **Keepalive socket port mismatch** (high priority, was M9 #1). Gateway's PUNCH_REPORT keepalive uses an ephemeral socket; reported endpoints carry the keepalive port not the listener port. Fix: either share Quinn's fd or encode the listener port explicitly in the PUNCH_REPORT.
2. **`ns register` missing `node_id` CBOR field** (low priority, was M9 #2). Pre-existing limitation; only affects bench gateways registered via the debug command. Production launch flow is unaffected.
3. **Loopback over-classification** (cosmetic, was M9 #3). `127.0.0.1` ranks at 160 (HostPublicV4) when operator opts in via `--advertise-all-interfaces`. Harmless to dial outcomes but wrong; classifier should filter loopback to priority 0.
4. **NEW — QuicDialer IPv4-only socket.** Probe socket binds `0.0.0.0:0` and fails on IPv6 candidates with EAFNOSUPPORT. Fix: dual-stack bind, or family-aware candidate filtering before dial.
