# v0.32.1 Z2LS bench validation — LAN-direct path PROVED green

> **Status:** ✅ PASS. Multi-candidate dial completes LAN-direct from TR-LAN orchestrator (10.69.95.13) to Z2LS (10.170.3.111) in milliseconds, with no relay fallback.

## Setup

- **Z2LS gateway:** `trs@10.170.3.111` (DESKTOP-LRC8DKH, x86_64 Windows). Service `ztlp_listener` running v0.32.1 binary under NSSM with `--advertise-all-interfaces`.
- **Orchestrator (dial side):** TR-LAN dev box `10.69.95.13`. Both boxes are on TR LAN but in different /24 subnets (`10.170.3.0/24` vs `10.69.95.0/28`) — neither sees the other as same-subnet, but both are mutually routable via the TR LAN gateway.
- **NS server:** Production NS at `16.147.41.195:23096` (v0.31.0). v0.32 PUNCH_REPORT frames are parsed transparently per the M8 back-compat tests.
- **Relay:** `34.218.240.106:23095` (production, v0.30.10).

## Evidence 1 — Z2LS publishes candidates at the LISTENER port (T1 verified)

`ztlp gateway candidates` against Z2LS from the orchestrator immediately post-deploy:

```
Candidates:
  PRIO  CLASS  ADDR
  200   host   [::1]:23095
  200   host   10.170.3.111:23095                              ← THE LAN ADDR
  200   host   [fdcf:bde3:2389:4a10:284b:333f:af72:b88f]:23095
  200   host   [fdcf:bde3:2389:4a10:ac94:93fb:7074:606c]:23095
  160   host   204.16.122.24:58260                             ← srflx (NAT-mapped, ephemeral)
  160   host   127.0.0.1:23095
```

**Critical observation:** every host candidate now carries port **`23095`** (the QUIC listener port). Pre-T1, these all carried port `50592` (the ephemeral keepalive socket port), which is exactly why every dial timed out on the v0.32.0 bench.

The single `:58260` outlier is the srflx address — the WAN-side NAT mapping for the keepalive socket — which is genuinely ephemeral and not affected by T1 (the source port for the keepalive packet is the keepalive socket's port, and that's what the WAN NAT mapped).

## Evidence 2 — Live multi-candidate dial succeeds LAN-direct (T2 + orchestration verified)

From the TR-LAN orchestrator `10.69.95.13`:

```
$ ztlp connect --multi-candidate --ns-server 16.147.41.195:23096 \
    --key ~/.ztlp/identity.json -vvv \
    z2ls-desktop-lrc8dkh-dcc1e2.z2ls-final-e2e.techrockstars.ztlp

Resolving z2ls-desktop-lrc8dkh-dcc1e2.z2ls-final-e2e.techrockstars.ztlp via ZTLP-NS...
  ✓ SVC record → 34.218.240.106:23095
  ℹ NodeID: bc97d655929c30be37885ff8de4881c8
  ✓ KEY record found
  Resolved: 34.218.240.106:23095

Connecting to: 34.218.240.106:23095
[v0.32] multi-candidate dial enabled (v0.32 experimental)
✓ multi-candidate dial succeeded: 10.170.3.111:23095 (HostOtherRfc1918)
```

- Initial NS-resolved address is the relay (`34.218.240.106:23095`) — the SVC record always points to relay.
- Multi-candidate dial fires, races all candidates in priority bands.
- **Winner: `10.170.3.111:23095` classified as `HostOtherRfc1918` (priority 200).** Direct LAN handshake.
- IPv6 candidates participated in the race (T2 fix) — no `EAFNOSUPPORT` panic, and the orchestrator didn't time out before trying them.
- Time-to-success: ~35ms wall (`punch: query NS` at 25.895s, multi-candidate succeeded by the next log line at the same second).

## Evidence 3 — Service stability

Z2LS service reached `Running` state cleanly post-deploy. UDP `0.0.0.0:23095` is bound. Existing relay registration flow continues (`Enabling QUIC gateway registration for relay: 34.218.240.106:23095` is logged on each restart cycle).

## What this PROVES

- **T1 (keepalive port plumbing):** verified end-to-end. Z2LS advertises `:23095` not `:50592`. Multi-candidate dial actually reaches the listener.
- **T2 (IPv6 dual-stack):** verified by absence of `EAFNOSUPPORT` errors in the dial; IPv6 candidates participate in the race even when an IPv4 one wins.
- **T3 + T4:** validated in CI (unit tests). No runtime evidence required — T3 is a regression test that already passed, T4 is a cosmetic priority-table change.

## What this DOES NOT PROVE (carry-forward)

- **Multi-candidate default-on safety:** the live dial succeeded on the first attempt because the host candidate wins fast. We have NOT stress-tested:
  - Behavior when the LAN-direct candidate is silently dropped mid-handshake (the orchestrator should fall back to relay).
  - Behavior with 8+ host candidates from a multi-NIC gateway.
  - Behavior under packet loss / bursty network conditions.
  
  These are validation tasks for the eventual v0.32.2 default-on flip.

- **iOS bench impact:** Steve's iOS bench was not running during this restart (per memory rule, would have been warned). iOS Z2LS interop on v0.32.1 is unvalidated.
