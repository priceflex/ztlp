# v0.33.0 — Client NS-record reachability fix

**Released:** 2026-05-28
**PR:** #75
**Type:** Bug fix + minor tuning. No wire-protocol changes. Fully backward compatible with v0.32.x clients (older clients keep working as-is against the upgraded NS).

## Problem

A device that ran `ztlp setup --token ...` against a v0.32.x NS would be unreachable by name after 60 minutes, even though it was still online and held a valid identity. Two interacting causes:

1. **Hardcoded 1-hour TTL on the enrollment path.** `ZtlpNs.Enrollment.register_device/5` wrote `ttl: 3600` directly into the KEY (and optional SVC) record for the new device, instead of going through `ZtlpNs.Server.default_ttl/1` which returns `86_400` for KEY/SVC. Every other registration path (regular `0x07 REGISTER` from the CLI, gateway service-records, bootstrap records) already used 24 hours. Enrollment was the outlier.

2. **3600 s rate-limit window equal to the TTL.** `ZtlpNs.RegistrationAuth.@rate_limit_window` was set to 3600 s. When a client tried to refresh its NS record before TTL expiry (the natural half-TTL refresh pattern), it landed inside the anti-flood cooldown and got `:rate_limited` back. So clients couldn't keep their records alive even if they tried — they had to wait for the record to actually expire, leaving a dead-zone window.

Net effect: any Mac/iOS/CLI device that enrolled at T=0 went unreachable by name between T=60min and T~=120min, then could re-register cleanly. For Steve's Mac Studio on the trs.ztlp tenant, this surfaced as "I'm enrolled and connected but the gateway can't resolve my name in audit logs after an hour."

## Fix

### A. Centralised TTL table (`ns/lib/ztlp_ns/record_defaults.ex`, new file)

New module `ZtlpNs.RecordDefaults` owns the per-record-type TTL constants. Single source of truth so the multiple registration paths can't drift again.

```elixir
def default_ttl(:key), do: 86_400       # 24h — was hardcoded as 3600 on enrollment path
def default_ttl(:svc), do: 86_400       # 24h — was hardcoded as 3600 on enrollment path
def default_ttl(:relay), do: 3_600      # 1h, intentional — gateways re-heartbeat
def default_ttl(:revoke), do: 0         # Never expires
# ...
```

### B. `enrollment.ex` uses the canonical helper

Two `ttl: 3600` literals at `ns/lib/ztlp_ns/enrollment.ex:329` and `:359` replaced with `ttl: ZtlpNs.RecordDefaults.default_ttl(:key)` and `(:svc)` respectively. New KEY/SVC records now get the full 24h TTL like every other registration path.

### C. `server.ex` delegates instead of duplicating

`ZtlpNs.Server.default_ttl/1` (10 lines of inline pattern matches) reduced to a one-line delegate so we have one place to update if the table ever needs to change.

### D. Rate-limit window 3600 s → 60 s

`ZtlpNs.RegistrationAuth.@rate_limit_window` changed from 3600 to 60. Preserves the anti-flood goal (no rapid churn from a runaway client) but lets legitimate half-TTL refreshes succeed. A new device half-TTL-refreshing every 12 hours will never collide with this window again.

## What this means for you

| Scenario | Before v0.33.0 | After v0.33.0 |
|---|---|---|
| Fresh enrollment | TTL=3600 s (1 hour) | TTL=86400 s (24 hours) |
| Refresh attempt 12h after enrollment | Rate-limited (3600s window not elapsed) | Accepted |
| Refresh attempt 30 s after enrollment (runaway client) | Rate-limited | Still rate-limited (60 s window) |
| Offline for 25 h then back online | Record was purged at T=60min anyway; rate-limit cleared; re-registers clean | Record purges at T=24h; rate-limit cleared; re-registers clean |
| Mac in active session that doesn't touch NS | Unreachable by name after T=60min | Unreachable by name after T=24h (still no client-side daemon yet) |

## What's NOT in this release (deferred to v0.33.1 / PR #76)

- **Client-side heartbeat daemon** (`ztlp register --daemon`) — would refresh KEY records every 12h to keep devices reachable indefinitely while running. Sized at ~80 lines of Rust plus launchd/systemd installer plumbing; deferred for proper design time.
- **Granular registration error codes** (`<<0xFF, <reason>>>` instead of opaque `<<0xFF>>`) — needed so the daemon can distinguish rate-limited from revoked from misconfigured. Will ship alongside the daemon since the daemon is the consumer.

- `ns/test/ztlp_ns/admin_test.exs` (extended): 2 new tests pinning the 60-second rate-limit window — `61 s ago = allowed`, `30 s ago = blocked`.
- All 54 existing `admin_test.exs` tests still pass.
- All 19 existing `enrollment_test.exs` tests still pass.

## Deployment

- Rebuild `priceflex/ztlp-ns:v0.33.0` from the upgraded Elixir source.
- Restart the `ztlp-ns` container on shared NS hosts (16.147.41.195 for SaaS).
- **WARN BEFORE NS RESTART** if iOS bench is running (per Steve's standing direction).
- No client CLI rebuild required for this release. v0.32.x clients continue to work and will benefit from the longer TTL automatically.

## Backward compatibility

- Wire protocol: unchanged.
- NS record format: unchanged.
- CLI ↔ NS interaction: identical bytes on the wire.
- Older clients (v0.32.x and earlier) talking to a v0.33.0 NS: ✅ work fine, get 24 h TTL on their KEY records.
- New v0.33.0 clients talking to a v0.32.x NS: ✅ work fine, get 1 h TTL (the bug). Upgrade the NS to benefit.
