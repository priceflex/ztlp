## 3. BY-DESIGN (not a vuln — correct architecture / documented tradeoff)

| Finding | Why it's by-design |
|---------|--------------------|
| Cleartext cert issuance over UDP (CWE-319) | The NS↔gateway/client channel is **UDP by architecture** and **signature-authenticated** (Ed25519). "Encrypting UDP" would require redesigning the transport; the signature already provides integrity + authenticity. |
| CA bootstrap TOFU (CWE-345) | Bootstrap is **trust-on-first-use** by definition — you can't validate the first root against a trust anchor you don't have. The fix (pin existing CA, reject later mismatch) is the documented trust model, same as SSH host keys. |
| NS records over signed UDP (CWE-345) | NS responses are **signed**; replay/forge rejected by signature check. |

## 5. Residual trust boundary (documented, follow-up for 0.36.0)

**CA cert issuance authorizes the component, not the hostname.** Per independent
triage, the `verify_cert_issuance_auth/3` checks authenticate the requesting
*component* and bind its signature to the hostname, but they do **not**
independently establish hostname ownership: `ComponentAuth.allowed_keys/0` is a
flat list of pubkeys with **no per-hostname binding** (component_auth.ex:325-327).
Consequently **any allowlisted component may request a cert for ANY hostname**.

This is **secure by design only if every allowlisted component is trusted to
request certs for any permitted hostname** — the same trust assumption as
"an operator-enrolled gateway key grants gateway capabilities." It is an
acceptable posture for a single-operator deployment (the allowlist is explicitly
operator-managed), but if components should be restricted to specific
names/namespaces, the fix is an `allowed_component_key -> permitted hostname
patterns` authorization check before `issue_server_cert/2`.

**Classification:** documented residual boundary — NOT a vuln in the 0.35.4
trust model, but a real hardening gap. Adding the binding changes the
`component_auth_allowed_keys` config schema (and the client/gateway that
populates it), which is a **config/protocol change → 0.36.0 workstream** (same
reasoning as the cert-issuance-replay protocol deferral). The regression pin
(`cert_issuance_auth_test.exs`) locks the *current* authorized-component model.

| Cert-issuance replay (CWE-294, ns) | **BY-DESIGN-DEFERRED** (protocol change) | A proper fix requires a **wire-format change** (timestamp in the signed message) + coordinated gateway update. The Rust↔Elixir wire format was *just* made to agree this session (the auth-tag nonce fix); flipping it now risks breaking the working interop. Not appropriate for a patch release. Recommend a dedicated 0.36.0 protocol workstream. |

| DoS / unbounded-buffer findings (CWE-770) | **Mostly already-bounded** | Several already have bounds (SAST markers); the rest are lower-priority hardening tracked in the prior remediation pass. |
